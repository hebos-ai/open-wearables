## Overview

Open Wearables is read-first. **Planned workouts** is an optional write capability: you describe a structured workout once, in a provider-agnostic format, and Open Wearables translates it for the provider the athlete is connected to.

| Provider | Support |
|----------|---------|
| Wahoo | ✅ Biking and running (plan library + scheduling) |
| COROS | 🔜 Scaffold, pending COROS partner API access |
| Others | ❌ Endpoint answers `501` |

## Canonical workout

The same JSON is accepted for every provider, in `camelCase` or `snake_case`. It matches the canonical workout used by Garmin Training API connectors, so one client can feed every translator.

| Field | Type | Notes |
|-------|------|-------|
| `name` | string (1–100) | |
| `sport` | string | `bike`, `mtb`, `indoor_cycling`, `run`, `trail_running`, `treadmill`, … Each provider rejects sports it cannot express |
| `steps[]` | 1–200 items | Steps, or repeat groups (below) |
| `steps[].kind` | `warmup` · `interval` · `recovery` · `cooldown` · `rest` | |
| `steps[].durationSec` | integer > 0 | Ends the step after this time… |
| `steps[].distanceM` | number > 0 | …or after this distance (never both). With neither, the step is open (lap button) |
| `steps[].target.type` | `power` · `hr` · `pace` | Optional |
| `steps[].target.low` / `high` | number > 0 | At least one; a single bound means "hold this value" |
| `steps[].name` | string (1–100) | Optional step label ("Work", "Jog") |
| `steps[].note` | string (1–500) | Optional note (providers without a per-step note field drop it) |
| `steps[]` repeat group | `{"kind": "repeat", "repetitions": 1–99, "steps": [1–50 steps]}` | The group runs `repetitions` times, in order. One level deep. Providers map it to their **native** repeat (not flattened) |

**Units are absolute** so translators never need athlete thresholds: power in **watts**, heart rate in **bpm**, pace as **speed in m/s** (same convention as Garmin Training API).

## Endpoint

`POST /api/v1/providers/{provider}/users/{user_id}/planned-workouts` (API key required)

```bash
curl -X POST "http://localhost:8000/api/v1/providers/wahoo/users/2b1f7c9e-3f0e-4c55-9a52-0c3f8f0d6a11/planned-workouts" \
  -H "X-Open-Wearables-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "workout": {
      "name": "Sweet spot 2x10",
      "sport": "bike",
      "steps": [
        {"kind": "warmup",   "durationSec": 600, "target": {"type": "power", "low": 120, "high": 160}},
        {"kind": "interval", "durationSec": 600, "target": {"type": "power", "low": 230, "high": 245}},
        {"kind": "recovery", "durationSec": 300, "target": {"type": "power", "high": 140}},
        {"kind": "interval", "durationSec": 600, "target": {"type": "power", "low": 230, "high": 245}},
        {"kind": "cooldown", "durationSec": 420}
      ]
    },
    "scheduledAt": "2026-10-12T07:00:00+02:00",
    "externalId": "plan-2026-10-12-sweetspot",
    "description": "Tempo build, week 3"
  }'
```

| Field | Notes |
|-------|-------|
| `workout` | Canonical workout (above) |
| `scheduledAt` | Optional, timezone-aware. Without it the workout only goes to the athlete's library |
| `externalId` | Optional stable id from your system (`[A-Za-z0-9._:-]`, ≤ 100); sent to the provider as its external id / token. **Re-sending the same id replaces** the workout. Generated when omitted |
| `description` | Optional |

**201** response:

```json
{
  "provider": "wahoo",
  "status": "scheduled",
  "external_id": "plan-2026-10-12-sweetspot",
  "provider_plan_id": "777",
  "provider_workout_id": "4242",
  "scheduled_at": "2026-10-12T05:00:00Z"
}
```

| Status | Meaning |
|--------|---------|
| `201` | Created (`status: created`) or scheduled (`status: scheduled`) |
| `401` | User not connected to the provider, or must re-authorize (e.g. connected before write scopes were requested) |
| `422` | Invalid canonical workout, or not expressible by the provider (e.g. `swim` on Wahoo, open step on Wahoo) |
| `501` | Provider does not support planned workouts |
| `502` | The provider did not complete the push (any provider error other than `401`). `detail.provider_plan_id` is set when the plan exists; re-send with the same `externalId` and that plan is updated, not duplicated |
| `503` | Another push/delete of the same `externalId` is still running (waited 60 s); retry later |

<Warning>
The API key is a backend credential with access to every user. This endpoint **writes to the athlete's provider account**, so call it only from your backend, never from end-user clients.
</Warning>

The push is synchronous. Open Wearables remembers what each `externalId` became on the provider (`planned_workout_push` table), so:

- **Re-sending the same `externalId` replaces** the workout: the same provider plan/workout is updated (content and date), never duplicated. Objects the athlete deleted on the provider side are re-created. Without `scheduledAt`, an earlier scheduled entry is taken off the calendar.
- Pushes and deletes of one `externalId` are serialized (Postgres advisory lock).

## Delete

`DELETE /api/v1/providers/{provider}/users/{user_id}/planned-workouts/{externalId}` (API key required) removes the workout from the athlete's calendar and library.

```json
{"provider": "wahoo", "external_id": "plan-2026-10-12-sweetspot", "deleted": true}
```

Idempotent: an `externalId` with nothing on record answers `200` with `deleted: false`. Objects already gone on the provider (`404`) count as removed. `401` not connected / re-authorize, `501` provider without planned workouts, `502` any other provider error (the record is kept so the delete can be retried), `503` another push/delete of the same id is running.

## Wahoo mapping

| Canonical | Wahoo plan.json |
|-----------|-----------------|
| `sport` | `header.workout_type_family` (0 biking, 1 running), `header.workout_type_location` (indoor for `indoor_cycling` / `treadmill`, otherwise outdoor) |
| `kind` | `intensity_type`: `wu` / `active` / `recover` / `cd` / `rest` |
| `durationSec` / `distanceM` | `exit_trigger_type` `time` / `distance` |
| `power` / `hr` / `pace` | target `watts` / `hr` / `speed` |
| `name` | interval `name` (default: the kind, e.g. "Warm up"). `note` is not sent: plan.json has no per-step note |
| repeat group | parent interval with `exit_trigger_type: "repeat"`, `exit_trigger_value: repetitions` and the group's steps in nested `intervals` |

Re-send: `PUT /v1/plans/{id}` and `PUT /v1/workouts/{id}` (a `404` re-creates with `POST`). Delete: `DELETE /v1/workouts/{id}`, then `DELETE /v1/plans/{id}`.

Scheduling uses `workout_type_id` 0 (biking), 13 (MTB), 61 (indoor trainer), 1 (running), 4 (trail), 5 (treadmill); `minutes` is estimated from step durations (distance steps count only when they have a pace target).

## Adding a provider

1. Subclass `BasePlannedWorkoutsTemplate` (`app/services/providers/templates/base_planned_workouts.py`) in `app/services/providers/<provider>/planned_workouts.py`.
2. Implement `translate()` — **pure**, canonical → provider payload; raise `PlannedWorkoutTranslationError` for anything the provider cannot express (never approximate silently).
3. Implement `send()` with `self._make_api_request(..., json_data=... | form_data=...)` and return a `PlannedWorkoutPushResult`. When `existing` is given (same `externalId` pushed before), **update** those provider objects instead of creating new ones, and call `self._record(...)` as soon as each provider object exists.
4. Implement `remove()`: delete what `existing` points to (treat `404` as already gone).
5. Set `self.planned_workouts = YourPlannedWorkouts(...)` in the strategy; `supports_planned_workouts` becomes `True` and the endpoint starts accepting the provider.
6. Unit-test `translate()` with plain objects and `send()` with a patched `_make_api_request`.
